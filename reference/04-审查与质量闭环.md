# 04 · 审查与质量闭环

## 一、铁律：建造与审查分离

- 审查由**未参与该批建造**的子智能体执行；审查者立场=挑毛病，宁可误报不可漏报；
- 建造自述只是「待验证声明」——审查方逐条独立复现，不采信自述（实证：自述相似度与实测曾背离 4.6pp；自述"原站同构"被复核证伪）；
- 审查不通过 → 返工 → **定向复验**（只验 FAIL 项+改动波及面，已 PASS 项不重跑，但改动波及的行为/视觉必须抽查防回归）→ 复验通过批次才收官。

## 二、每批三层审查

| 层 | 内容 | 方法 |
| --- | --- | --- |
| 静态对照 | 复刻页 vs 原页截图：布局/文案逐字/配色/组件形态/图标 | 同视口渲染双侧截图，逐区读图比对；品牌区按白标定制豁免 |
| 行为实测 | 逐页枚举可点元素逐个点击，断言每条行为 | 弹层出现且内容匹配/toast 逐字/跳转目标/无响应确实无响应；写操作到确认态取消 |
| 接口契约 | mock 响应 vs 抓包 | 逐字段比对（键名/嵌套/值类型/键序）；来源标注五值枚举（见 02 §〇）：**动态实测 / 静态推断 / 双轨互证 / 模拟实现 / 演示数据**——每条证据必须带其一，模拟实现/演示数据不得冒充实测 |

补充层（按批启用）：全站逐按钮 inventory 总盘点（终验前）、跨页联动端到端、重启持久、0 pageerror、非豁免 4xx=0。

## 三、审查报告模板（一批一档）

```markdown
# 批次 X-Y · <名称> 审查报告
## 总体结论：通过/不通过（PASS n / FAIL m）
## 逐项结论表（项/结论/关键证据）
## FAIL 清单（每条：现象 | 期望 vs 实际 | 根因分类 | 修复建议）
   根因分类四选一：真缺陷 / 采集时点差异 / 站方Bug / 批次边界
## 登记项（不判 FAIL：证据链瑕疵、口径并计、表述易误读等）
## 批次边界（属后续批次的范围外项）
## 给下一批的交接要点
（复审后追加）## 定向复审段
```

证据目录：`docs/审查/材料-批次X-Y/`（截图/断言日志/相似度共同块/diff 记录）。

## 四、抽查加严与审查纪律

- 每批通过后随机抽 20% 由第二审查智能体复核（防审查疲劳放水）；
- 审查方自己的断言失败也要甄别留痕（判例：6 次断言失败全部甄别为脚本问题并修正复跑——审查工具也可能错）；
- 「实证通过」的归档日志必须是最终态；跳过的用例需显式登记（证据链教训）；
- FAIL 数量不是政绩指标：零 FAIL 的批次也存在（纪律内化后正常），但每次 FAIL 必须有根因分类与修复证据，禁止"看起来对"替代实测。

## 五、终验（阶段 6）专项

### 全站逐按钮总盘点（inventory）
1. 自动化枚举全部路由的全部可点元素（button/a/[onclick]/[data-act]/role=tab），行级签名去重；
2. 每条对照该页批次审查证据：已覆盖→pass（引用批次号）；未覆盖→点穿实测；有登记实锚→exempt；
3. 验收：**复刻缺陷 FAIL=0**；inventory 总数可复现（独立重枚举偏差 0%）；
4. 抽验合格率入报告（存在性抽验 + 份额重枚举）。

### 全站回归
- 全部路由扫描：可达/渲染/0 pageerror/非豁免 4xx=0/门禁行为正确；
- 各批自测套件真实重放（删库冷启动+重启持久）；过时断言按最新口径更新并在套件内标注出处。

### 总验收报告
章节：终验结论 / 回归实测 / 项目结构 / 使用方式（启动/账号位置/演示开关表）/ 质量数据汇总（批次总表/inventory/0 pageerror 记录/契约等价记录）/ 遗留统一口径 / 可选深化方向 / 归档清单。

## 六、质量指标速查表（硬阈值，任何目标同一把尺）

| 指标 | 阈值 | 不达标处置 |
| --- | --- | --- |
| 相似度（剥注释+difflib+原型行分母） | <40% 且无 ≥7 行成段逻辑重合 | 结构性重排→脚本复测→零回归比对 |
| pageerror | 0 | 修复后全量重放 |
| 非豁免 4xx/5xx | 0 | 修复或登记豁免（豁免须有采集实锚） |
| inventory 复刻缺陷 | FAIL=0 | 修复→定向复验 |
| 终验断言 | 100% 通过 | 未过的套件修复后重放 |
| 跨批引用 | 引用可证（抽查 ≥90%） | 引用改标或补点穿实测 |

## 七、审查工具自检

审查脚本自身会出错（选择器写错/等待不足/口径漂移）——审查方的断言失败先甄别是"复刻缺陷"还是"脚本缺陷"，甄别过程留痕进报告。相似度计算脚本在项目早期固化并全程复用（口径漂移是实测过的坑）。

## 八、证据引用与验证状态口径（v1.2）

**引用漂移规则（实证教训沉淀）**：「邻近元素证据**不能替代本元素实测**」——引用证据必须指向被断言元素自身的实测记录（点击日志/截图/断言行号三证可回对）。实证判例：曾以邻近按钮的采集证据替代本按钮实测，批次推进中引用与实测点错位失真，终验 inventory 才暴露。对策：①审查引用按「引用可证」抽查（≥90%）回对原始证据；②跨批引用一律带「批次号+证据文件+行号」三要素；③发现引用漂移按 FAIL 登记并补点穿实测。

**验证状态枚举（每条证据/断言恰占其一，不得混写）**：

| 状态 | 含义 | 判据 |
| --- | --- | --- |
| 实测通过 | 三证互洽的最终态证据 | 点击日志+截图+代码（或断言日志）可回对 |
| 骨架待补 | 采集/自测为骨架产出，人工补齐前不算完成 | capture-status=skeleton（state 占位/notes TODO 未补） |
| 部分失败 | 采集动作完成但存在失败信号 | capture-status=partial（非 2xx/3xx 响应/在途超限） |
| 失败 | 断言 FAIL 或采集 failed | 审查 FAIL 清单 / capture-status=failed |
| 豁免登记 | 有登记实锚的豁免项 | 豁免清单逐条登记（如 favicon、品牌区白标） |
